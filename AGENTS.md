# Agent Guidelines (Repo)

This document is the canonical guide for how code is organized in this repository and the conventions agents should follow when making changes.

## Project Overview

This project is a Go API that follows a layered architecture (clean/hexagonal style):

- **Domain** is the center (entities + business rules).
- **Application** coordinates use cases (services).
- **Interfaces/Adapters** expose the system (HTTP) and connect to external systems (DB).

The goal is to keep the domain and use cases stable while infrastructure and transport details remain replaceable.

## Repository Layout (High Level)

- `cmd/`: entrypoints (binaries). Example: `cmd/api/main.go`.
- `internal/`: application, domain, and adapters (not importable by external modules).
- `pkg/`: stable, reusable, non-domain utilities intended to be shareable and dependency-light.
- `docs/`: Swagger artifacts generated by `swag` (do not edit manually).

## Layering Rules (Imports)

Keep dependencies pointing inward:

- `internal/domain` **must not** import from `internal/application`, `internal/infra`, or `internal/interfaces`.
- `internal/application` may import `internal/domain` and ports (`internal/interfaces/...`), but must not depend on concrete infra (DB/Gin).
- `internal/interfaces` contains adapter code (HTTP handlers and repository ports/errors).
- `internal/infra` contains concrete implementations (e.g., Gorm repositories, DB connection).
- `pkg/` must never import anything from `internal/`.

If you need to share code, prefer **moving it to the appropriate layer** rather than introducing cross-layer imports.

## HTTP Layer Conventions (`internal/interfaces/http`)

### Controllers (`internal/interfaces/http/controllers`)

Controllers are thin:

- Parse request input (path/query/body).
- Call the appropriate application service.
- Convert domain objects to DTOs (via `mapper`).
- Write HTTP responses and status codes.
- Keep HTTP concerns here (Gin context, status codes, JSON errors).

Controllers should not:

- Contain complex mapping logic (belongs in `mapper`).
- Contain DTO definitions (belongs in `dto`).
- Contain business rules (belongs in `domain`/`application`).

Shared controller helpers (pagination, error mapping) belong under `internal/interfaces/http/shared` (not `pkg/`, because they are Gin/internal-coupled).

### DTOs (`internal/interfaces/http/dto`)

DTOs define the external HTTP contract (JSON):

- Requests: `CreateXRequest`, `UpdateXRequest`, etc.
- Responses: `XResponse`, `XListResponse` if needed.

Rules:

- DTOs are transport-specific and may include `binding:` tags.
- DTOs should avoid importing infrastructure packages.
- Swagger annotations in controllers should reference DTO types (e.g., `dto.ClientResponse`).

### Mappers (`internal/interfaces/http/mapper`)

Mappers translate between domain types and DTOs:

- Prefer pure functions like `XResponseFromDomain(domain.X) dto.XResponse`.
- Keep mapping logic centralized here so controllers remain small and consistent.
- Mapper functions should not touch Gin, DB, or other side effects.

### Shared HTTP Helpers (`internal/interfaces/http/shared`)

Shared HTTP utilities that are Gin/internal-specific live here, e.g.:

- Pagination parsing (`limit`/`offset`).
- Translating repository errors into consistent HTTP error responses.

## Repository Ports and Errors (`internal/interfaces/repository`)

This package defines repository-level errors and (optionally) interfaces/ports used across layers.

Conventions:

- Keep sentinel errors like `ErrNotFound`, `ErrConflict` here.
- Application/services and controllers can translate these errors into use-case/HTTP responses.

## Application Layer (`internal/application`)

Application services orchestrate use cases:

- Validate high-level invariants and coordinate repositories.
- Avoid HTTP/Gin concerns.
- Avoid direct Gorm/DB access; use repository implementations through ports or concrete types where the project’s architecture allows.

The application layer should be where “what the system does” lives, without being tied to “how it’s exposed” (HTTP) or “how it’s stored” (DB).

## Domain Layer (`internal/domain`)

Domain packages define core concepts:

- Entities/value objects (e.g., `client`, `vehicle`, `order`).
- Domain-specific types and invariants.

Rules:

- Keep domain free of framework dependencies.
- Prefer explicit types (e.g., `DocumentType`) over unstructured strings where meaningful.

## Infrastructure Layer (`internal/infra`)

Concrete integrations live here:

- DB connection/migrations (`internal/infra/db`).
- Repository implementations (e.g., Gorm-based repositories).
- External services/adapters.

Infrastructure should not leak into domain types.

## Swagger (Documentation)

Swagger docs are generated from Go annotations and the main entrypoint metadata:

- Do not edit files under `docs/` manually.
- Regenerate using the repository commands (e.g., `make swagger`).

When moving DTO types, ensure Swagger annotations reference the new package paths (typically `dto.*`).

## `pkg/` Policy (What Belongs There)

Use `pkg/` for **stable, reusable, non-domain utilities** that may be shared across multiple layers/binaries **without importing anything from `internal/`**.

Good candidates:

- Input normalization helpers (e.g., BR documents/plates).
- Generic helpers that don’t depend on Gin/Gorm/app-specific services.

Currently extracted:

- `pkg/br/document`: digits-only normalization + CPF/CNPJ validation wrappers.
- `pkg/br/plate`: plate normalization (uppercase, remove spaces/hyphens).

Avoid putting in `pkg/`:

- Domain entities (`internal/domain/...`).
- Use cases / application services (`internal/application/...`).
- Repository ports (`internal/interfaces/repository/...`).
- HTTP controllers/middlewares (Gin-specific) and DB adapters (Gorm-specific).
- Anything that imports from `internal/`.

Rule of thumb:

- If it imports from `internal/`, it **does not belong** in `pkg/`.
- If it would lock us to Gin/Gorm, it probably belongs under `internal/` (adapter layer).

## Code Organization Matters (Why We Enforce This)

Maintaining a clean structure has practical benefits:

- Faster onboarding (predictable locations for changes).
- Smaller diffs (logic lives in one place).
- Less coupling (swapping transport/DB becomes feasible).
- Higher testability (domain/application can be tested without HTTP/DB).

When in doubt:

- Keep controllers thin.
- Put transport contracts in `dto/`.
- Put mapping in `mapper/`.
- Put reusable HTTP-only helpers in `shared/`.
- Keep `pkg/` strictly for stable, dependency-light utilities.
